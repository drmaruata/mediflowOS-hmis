# Mediflow OS HMIS

[![CI](https://github.com/drmaruata/mediflowOS-hmis/actions/workflows/ci.yml/badge.svg)](https://github.com/drmaruata/mediflowOS-hmis/actions/workflows/ci.yml)

[![React](https://img.shields.io/badge/React-18.3-61DAFB?logo=react&logoColor=white)](frontend/package.json)
[![PostgreSQL](https://img.shields.io/badge/PostgreSQL-15%2B-4169E1?logo=postgresql&logoColor=white)](#prerequisites)

Mediflow OS HMIS is a multi-tenant healthcare management information system designed for hospitals and clinics. The project combines a Django-based backend API with a Vite + React frontend to deliver modules for patient administration, operations, billing, pharmacy, reporting, quality indicators, and integration workflows.

It is built for Indian healthcare deployment: healthcare-worker sign-in with MFA and break-glass, India ABDM (ABHA) integration, and patient identifiers that are encrypted at rest, with every cross-tenant boundary enforced in the database and every audit entry tamper-evidently chained.

This repository is organized as a modular monolith, with the backend split into domain apps and the frontend built as a single-page application.

## Project overview

The application is built around the following principles:

- Multi-tenant healthcare workflows and tenant-aware data access
- Modular domain structure for clinical and operational areas
- REST API-first backend using Django REST Framework
- Realtime features using Django Channels and Redis
- Background jobs and scheduling through Celery and Redis
- PostgreSQL as the primary data store
- React frontend with Shadcn UI (Tailwind CSS) and Vite for a modern admin interface

## Key features

- **Tenant isolation in the database, not just in code.** Every request binds a
  tenant context via `set_config`, and [a dedicated CI job](.github/workflows/ci.yml)
  runs the cross-tenant read/write/fail-closed suite against real PostgreSQL row
  level security.
- **PHI protection.** Patient identifiers (`abha_number`, `abha_address`,
  mobile) are encrypted at rest with AES-256-GCM plus keyed-HMAC search indexes
  (REG-008); API permissions are deny-by-default and MFA is first-class.
- **Tamper-evident audit trail.** Every audit row extends an HMAC-SHA256 hash
  chain (AUD-002), verifiable through `GET /api/v1/audit-log/verify/`.
- **India ABDM (HIP) gateway.** Outbound ABHA create/verify (REG-009) and an
  authenticated callback flow that validates signatures, binds the tenant from
  the facility's HIP ID, is idempotent per gateway request, records consent
  (ABD-011) and stores the sealed link token (ABD-012).
- **19 domain apps.** Identity & tenancy, patient registry, OPD, IPD, emergency,
  ICU, operation theatre, LIS, RIS, pharmacy, blood bank, billing & insurance,
  EMR, quality OS, ABDM gateway, integration, audit, platform, realtime.
- **Realtime and background work.** Django Channels WebSocket consumers behind
  daphne (notifications, live vitals) and Celery + django-celery-beat workers
  with real retry and idempotency policies.
- **A typed, tested frontend.** React 18 + TypeScript (strict), shadcn/ui on
  Tailwind CSS v4 with design tokens, TanStack Query, React Router 7, Zod +
  React Hook Form, and 190+ Vitest unit/integration tests.
- **A spec you can trust.** The OpenAPI schema is generated by drf-spectacular
  and CI fails on warnings or an invalid document, so the published
  specification matches the code.

### UI system migration: Ant Design 5 → Shadcn UI (2 Oct 2026)

The frontend `frontend/` folder was deleted and re-scaffolded. Ant Design,
`@ant-design/icons`, and `@ant-design/charts` were **removed** and replaced
with Shadcn UI on Tailwind CSS v4. Rationale and the full decision table are
in `docs/SaaS HMIS Architecture v0.6.md` §14.1.

| Removed | Added | Why |
| --- | --- | --- |
| `antd` | `tailwindcss` + `@tailwindcss/vite` | Components are vendored source, not a compiled dependency; Tailwind owns the token system. |
| `@ant-design/icons` | `lucide-react` | Matches shadcn's default `iconLibrary`. |
| `@ant-design/charts` | *(nothing)* | Dashboard donut/bar charts are hand-rolled inline SVG, so no chart dependency is needed at all. |
| — | `@radix-ui/react-*` | Unstyled accessible primitives shadcn builds on. |
| — | `class-variance-authority`, `tailwind-merge`, `clsx` | Variant system and `cn()` class merging for the vendored components. |
| — | `components.json`, `src/components/ui/` | shadcn registry config plus the vendored component source. |

**Breaking change for contributors.** shadcn components are *source files you
own*, not a package you import. Upstream changes arrive only via
`npx shadcn@latest add <component> --diff`; never overwrite local edits without
reviewing the diff.

`sonner` is declared but the vendored Radix `Toast` component is used instead;
treat `sonner` as unused until a toast call site is written.

**Added shadcn components** (vendored in `frontend/src/components/ui/`):
`button`, `card`, `input`, `label`, `badge`, `avatar`, `dialog`, `tabs`,

### daphne (added during the tenancy and security hardening pass)

`daphne` is the ASGI server the application runs behind, and it is declared in
both `backend/requirements.txt` and `backend/pyproject.toml` as `>=4.2,<5`,
resolving to 4.2.3.

It was previously missing entirely: the project declares `ASGI_APPLICATION` and
serves Django Channels consumers for notifications and live vitals
(architecture doc section 13), but no ASGI server was installed or declared. A
WSGI server cannot serve a WebSocket consumer, so the image had no valid way to
start. `docker/Dockerfile.backend` uses it as the entrypoint.

If you run the application locally, start it with daphne rather than
`runserver`:

```bash
# From backend/, with the virtualenv active:
daphne -b 0.0.0.0 -p 8000 config.asgi:application
```

`python manage.py runserver` still works for ordinary HTTP development through
Django's ASGI handler, but it is not what the container uses.

## Prerequisites

Before setting up the project locally, install the following:

- Python 3.11 or newer
- Node.js 22.22.2+ or 24.15+ and npm (required by the frontend test environment)

- Git
- A terminal such as PowerShell, Bash, or zsh

- Docker Desktop (for container-based local development)
- pgAdmin or a SQL client for database inspection

### 3. Configure PostgreSQL and Redis

The project defaults to PostgreSQL and Redis values in the Django settings. For local development, ensure PostgreSQL is running and a database exists, for example:

```sql
CREATE DATABASE mediflow_dev;
```

Set the environment variables you want your app to use before starting Django. Example:

```powershell
$env:DJANGO_SETTINGS_MODULE = "config.settings.dev"
$env:DJANGO_SECRET_KEY = "local-dev-secret-key"
$env:DJANGO_DEBUG = "true"
$env:PGDATABASE = "mediflow_dev"
$env:PGUSER = "postgres"
$env:PGPASSWORD = "postgres"
$env:PGHOST = "localhost"
$env:PGPORT = "5432"
$env:REDIS_URL = "redis://localhost:6379/0"
$env:CELERY_BROKER_URL = "redis://localhost:6379/0"
```

> **PATIENT_FIELDS_KEY (REG-008):** patient identifiers (`abha_number`,
> `abha_address`, `contact.mobile`) are encrypted at rest with a key derived
> from `PATIENT_FIELDS_KEY`. For local dev this is optional — `config.settings.dev`
> supplies a deterministic development passphrase when the variable is unset —
> but it must be explicitly exported in any non-DEBUG environment: `base.py`
> refuses to start without it so identifiers are never encrypted under an
> empty or guessed key. Example:
>
> ```powershell
> $env:PATIENT_FIELDS_KEY = "a-long-random-passphrase-only-the-hospital-knows"
> ```

> **AUDIT_HMAC_KEY (AUD-002):** the audit trail is a tamper-evident
> HMAC-SHA256 hash chain — every row's `hash_chain` is `HMAC(key, prev_hash +
> canonical(fields))`, recomputed by `GET /api/v1/audit-log/verify/` — so this
> key is what makes the chain unspoofable: an unkeyed HMAC is just a hash, and
> without a real key anyone who can read `audit.event` could recompute, and
> therefore forge, the chain. It must be explicitly exported in any non-DEBUG
> environment: `base.py` refuses to start without it (`ImproperlyConfigured`),
> mirroring the `PATIENT_FIELDS_KEY` guard above, so the failure is a
> refusal to start rather than a silently unverifiable log.
> `config.settings.dev` and `config.settings.test` supply deterministic
> values, so a local database keeps verifying across restarts (a random key
> per boot would be a silent rotation every start). A note on DEBUG: with
> `DEBUG=true` the variable is *tolerated* at settings import, but an empty
> value leaves the chain unrunnable — `_hmac_key` raises on every append and
> verify — so the practical dev state is the deterministic value
> `config.settings.dev` installs, not a hand-exported empty one. Example:
>
> ```powershell
> $env:AUDIT_HMAC_KEY = "$([Guid]::NewGuid().ToString('N') * 2)"
> ```
>
> **AUDIT_RETENTION_DAYS (AUD-004):** how many days of audit history the
> retention purge keeps (`purge_expired`), defaulting to **365** when unset
> and overridable per deployment. The SRS requires "a configurable retention
> policy" without naming a period, and the architecture doc leaves long-term
> audit retention open with the customer (OQ-08), so 365 is a documented
> placeholder, not a compliance claim. A non-numeric or non-positive value
> falls back to the default rather than silently disabling or widening the
> purge. Example:
>
> ```powershell
> $env:AUDIT_RETENTION_DAYS = "2555"  # seven years, a common statutory floor
> ```
>
> **MAX_UPLOAD_MB (PLT-005):** the size cap, in megabytes, for a single
> document uploaded to `POST /api/v1/files/`, defaulting to **10** when unset.
> The API also rejects extensions outside an allow-list (pdf, png, jpg, csv,
> json), so this is the cap on a *documented-type* upload rather than the
> first check to fire. A hostile **filename** is not rejected: it is renamed
> into one safe path component under a server-generated per-upload directory,
> because refusing it would tell the sender their name was interesting, and the
> stored path is inside the tenant's own directory either way. The **download**
> route is the one that refuses a stored path — with a 404 — when it does not
> resolve under `MEDIA_ROOT`, or when its first component is not the tenant that
> owns the row. A non-numeric or non-positive value falls back
> to the default rather than silently disabling the cap. Example:
>
> ```powershell
> $env:MAX_UPLOAD_MB = "25"  # a facility scanning large multi-page reports
> ```
>
> **MEDIA_ROOT (PLT-005):** the absolute filesystem directory that uploaded
> documents live in, defaulting to `<repo>/backend/media`. Each document is
> stored under `<tenant_id>/<upload-uuid>/<sanitised filename>` there, so the
> tenant partition is part of the path and two same-named uploads from one
> hospital never collide. `config.settings.test` overrides this to a per-run
> temporary directory so the suite never writes into the working tree. Example:
>
> ```powershell
> $env:MEDIA_ROOT = "D:\mediflow\uploads"  # a mounted volume in production
> ```
>
> **OIDC_ISSUER / OIDC_AUDIENCE / OIDC_JWKS_URI / OIDC_TENANT_CLAIM /
> OIDC_JIT_PROVISION (INT-009):** single sign-on via `POST /api/v1/auth/oidc/`,
> which exchanges an OIDC ID token — issuer, audience, signature and expiry
> all verified against the IdP's published JWKS — for the same token pair
> `auth/token/` issues. The first three are required: with any of them unset
> the endpoint answers **501** with a structured body before any verification
> work, never a fake 200. `OIDC_TENANT_CLAIM` names the ID-token claim carrying
> the tenant **slug** to bind (default `tenant`); an absent or unresolvable
> claim is refused with 403, and there is no default-tenant fallback.
> `OIDC_JIT_PROVISION` (`true`/`false`, default **false**) opts in to
> just-in-time account creation on first sign-on: while it is off an unknown
> identity is refused with 403. Example:
>
> ```powershell
> $env:OIDC_ISSUER = "https://sso.hospital.example"
> $env:OIDC_AUDIENCE = "mediflow-hmis"
> $env:OIDC_JWKS_URI = "https://sso.hospital.example/.well-known/jwks.json"
> $env:OIDC_JIT_PROVISION = "true"   # create accounts on first sign-on
> ```

> The project defaults to PostgreSQL on `localhost` and Redis at `redis://redis:6379/0` in many settings. If you are using local services instead of containers, update these values accordingly.

## Suggested local workflow

For standard development, use this flow:

1. Start PostgreSQL and Redis locally.
2. Activate the backend virtual environment.
3. Run `python manage.py migrate`.
4. Start the Django server with `python manage.py runserver 0.0.0.0:8000`
   (or `daphne -b 0.0.0.0 -p 8000 config.asgi:application` for WebSockets).
5. Start Celery worker(s) if background jobs are needed.
6. Start the frontend with `npm run dev`.
7. Open the frontend in the browser and verify API calls through the Django backend.

For local validation, run `npm run check` from `frontend/`, and run `python -m pytest` plus `python -m ruff check . ../tests` from `backend/`. Pytest uses `config.settings.test` with in-memory SQLite and does not need external services.

## Notes on architecture

This repository follows a modular monolith design:

- Domain logic is grouped under `backend/apps/`
- Shared policies live in `backend/common/`
- Tenant-aware middleware and utilities handle cross-cutting concerns
- API schema is generated from DRF endpoints with `drf-spectacular`
- Realtime and cache concerns rely on Redis
- Clinical and operational services are organized by module like `patient_registry`, `opd`, `ipd`, `pharmacy`, `lab`, `billing`, and `quality_os`

## Troubleshooting

### Database connection errors

Verify that PostgreSQL is running and your environment variables match your local database credentials.

### Redis connection errors

Check that Redis is installed and running locally, and confirm the `REDIS_URL` / `CELERY_BROKER_URL` values.

### Frontend cannot reach the backend

Make sure the frontend API base URL matches the backend. If your frontend is configured to call a different host, update the relevant configuration or proxy settings.

### Missing dependencies

If Python or npm packages are missing, reinstall them using:

```bash
pip install -r backend/requirements-dev.txt
npm ci --prefix frontend
```

## Production and deployment notes

This project is not yet a full production deployment template in the repository. For deployment, you should typically:

- Replace local environment variables with secure production values
- Configure a managed PostgreSQL database
- Configure a managed Redis instance
- Set `DJANGO_DEBUG=false`
- Use a production WSGI/ASGI deployment strategy
- Run `python manage.py collectstatic` for static asset serving
- Configure Celery workers and beat in a process manager or container orchestration layer
- Restrict CORS and trusted origins via environment settings

## Contributing

Development rules live in [AGENTS.md](AGENTS.md) — the short version:

1. **Verify before you write.** Library APIs are checked against current
   documentation, and the pinned stack (Django 5.2 LTS, DRF 3.18, React 18,
   Vite 6, Tailwind CSS v4) is not upgraded silently — stay inside the tested
   major versions.
2. **Land work behind the gates.** `npm run check` (lint + typecheck + Vitest)
   in `frontend/`; `python -m pytest` and `python -m ruff check . ../tests` in
   `backend/`. New tenant-owned endpoints need cross-tenant isolation tests and
   stay deny-by-default.
3. **Conventional Commits with a scope** — `feat(dashboard): …`,
   `fix(security): …` — matching the existing history.
4. **Keep documents in sync.** Any dependency or tooling change updates the
   manifests **and** the relevant docs (`README.md`, `AGENTS.md`) in the same
   commit; a green suite with stale docs is still a rejected change.
5. **Migrations are expand-then-contract.** Never edit an applied migration,
   and never drop/rename a column in the release that stops writing it.

Every push to `main` and every pull request runs
[.github/workflows/ci.yml](.github/workflows/ci.yml): backend lint and Django
checks, the service-free test suite, a dedicated cross-tenant **RLS isolation**
job against real PostgreSQL, frontend check plus production build, a container
image build with a health-probe smoke test, and dependency review with
`pip-audit`. CI green is the baseline for merge.
